De drie paden van een betaling

Een "Ogone-betaling" in nl-portal is een taak (TaakSoort.Ogonebetaling) die de gebruiker naar Worldline (voorheen Ogone) stuurt om af te rekenen — bijvoorbeeld leges voor een aanvraag. Voor code review is het belangrijkste inzicht: er zijn drie afzonderlijke componenten die elk hun eigen deel van de betaling bewaken, en ze lopen niet gelijktijdig.

Waarom twee paden naar dezelfde conclusie?

Pad A is wat de gebruiker ziet: na betalen stuurt Worldline de browser terug naar nl-portal met ?type=ogone&hostedCheckoutId=.... De frontend-hook usePaymentRegistration vraagt dan via getDirectPaymentStatus de status op bij Worldline.

Pad B is een server-naar-server webhook: Worldline doet zelf een POST naar /api/public/payment/direct/postsale, ongeacht of de gebruiker ooit terugkeert. Dat eindpunt (DirectPaymentController) delegeert naar DirectPaymentWebhookService, die de taakstatus in de Objecten API bijwerkt.

Waarom dit ertoe doet bij een review

Pad A is niet betrouwbaar genoeg om de taakstatus op te baseren: de gebruiker kan het tabblad sluiten, de betaalpagina crashen, of terugkomen met een gemanipuleerde URL. Pad B (de webhook, met handtekening- validatie) is de bron van waarheid voor "is er betaald". Pad A is alleen voor de gebruikerservaring (wat laten we zien terwijl we wachten). Zie je een PR die de taakstatus laat afhangen van het redirect-pad in plaats van de webhook — dat is een rode vlag.
